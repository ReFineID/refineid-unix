# Internationalization (i18n) and localization (l10n)

How refineid handles user-facing prose across English, suomi,
and svenska without coupling code to any specific locale.

This is the canonical policy. Code that emits or stores
human-readable strings should reference this doc; the rules
here are not duplicated in code comments or in agent memory
([`AGENTS.md`](../AGENTS.md) §9).

## Two disciplines, one pipeline

**i18n (internationalization)** is the *engineering* structure.
The codebase carries values in locale-agnostic strong types and
routes them through a renderer that can produce any locale's
form. Code does not know that `2022-10-24` is "Finnish-natural"
or "American-natural" -- it knows the value is a `Date` and
delegates rendering.

**l10n (localization)** is the per-locale *content*: the actual
prose templates, date-format rules, number-format rules,
pluralization, case agreement. Lives in bundle files, separate
from code, editable by people who don't read Rust.

The split matters because:

1. Engineering code must not become locale-bound. A bug in
   Finnish punctuation should not require a Rust recompile.
2. Translators must not need a Rust toolchain to fix a typo.
3. Audit logs must carry the canonical engineering form
   (ISO 8601 dates, lowercase hex fingerprints, digit strings)
   so a SOC parser six time zones away can read them without
   knowing what locale the operator was running in.
4. The same `Date` value must round-trip across all three
   locales without information loss. Storing
   `"24.10.2022"` on the wire would lose the engineering form.

See also [[feedback-strong-typing-as-security]] and
[`doc/typing-discipline.md`](typing-discipline.md): the same
discipline that keeps PIN bytes typed keeps locale-specific
strings out of engineering code.

## Engineering-canonical forms

The structured event payload (the flat key-value JSON-Lines
record from [`doc/observability.md`](observability.md)) uses
*engineering-canonical* forms for every data field,
**regardless of operator locale**:

| Domain          | Canonical form           | Example                                 |
|-----------------|--------------------------|-----------------------------------------|
| Date            | ISO 8601 `YYYY-MM-DD`    | `"card_issued": "2022-10-24"`           |
| Time            | ISO 8601 `HH:MM:SSZ`     | `"checked_at": "2026-05-24T09:11:22Z"`  |
| Hash / digest   | lowercase hex            | `"trust_root_sha256": "d3ed3fc4..."`    |
| Integer count   | decimal digit string     | `"wrong_tries_to_lock": "5"`            |
| Country         | ISO 3166-1 alpha-2 / ICAO 9303 alpha-3 | `"csca_country": "FI"`    |
| Enum (domain)   | canonical lower_snake_case identifier  | `"card_generation": "older"` |

These are stable across locales. A Finnish operator reading
the log and a Swedish operator reading the log see identical
data fields; only the `human.*` fields differ.

## Human-readable forms: bundle-rendered

Human-readable prose lives in a per-locale bundle, not in
code. Code emits a *message ID* and *typed arguments*; the
renderer reads the locale's bundle, substitutes the args, and
produces a string. Code never writes:

```rust
format!("Card issued {}, older generation", iso_date)         // anti-pattern
format!("Kortti myönnetty {}, vanhempi sukupolvi", iso_date)  // anti-pattern
```

Code writes:

```rust
events::CardActivatePreflightReady {
    card_issued: ctx.issuance_date,        // typed Date
    card_generation: CardGeneration::Older, // typed enum
    activation_pin_length: 8u8,
    // ...
}
.emit();
```

The renderer takes the typed values and renders three
locale-specific strings via the bundle templates, attaching
them to the event as `human.en`, `human.fi`, `human.sv`.

### Locale-specific rendering of typed values

The renderer is responsible for projecting engineering-canonical
values into each locale's natural form. Examples:

| Type / value | en presentation       | fi presentation     | sv presentation     |
|--------------|-----------------------|---------------------|---------------------|
| `Date(2022, 10, 24)` | `October 24, 2022` or `2022-10-24` | `24.10.2022`        | `2022-10-24`        |
| `1234567`            | `1,234,567`           | `1 234 567`         | `1 234 567`         |
| `CardGeneration::Older` | `older-generation` | `vanhempi sukupolvi`| `äldre generation`  |
| `CardGeneration::Newer` | `newer-generation` | `uudempi sukupolvi` | `nyare generation`  |
| `PinSlot::Pin1`         | `basic PIN`        | `perustunnusluku`   | `baskod`            |
| `PinSlot::Pin2`         | `signature PIN`    | `allekirjoitustunnusluku` | `signaturkod` |

DVV vocabulary (`aktivointitunnusluku`, `aktiveringskod`, etc.)
is canonical for the fi/sv strings -- see
[`doc/dvv-terminology.md`](dvv-terminology.md). "American
SSN"-style mistranslations of *henkilötunnus* are reviewed out;
PIC is the English form.

## Bundle layout

```
locale/
  en/refineid.ftl
  fi/refineid.ftl
  sv/refineid.ftl
```

One file per locale at the workspace root. Each file is the
full set of message templates for that locale; missing
entries fail the build (every event ID must resolve in every
locale -- see "Open decisions" below for how exactly we
enforce this).

Adding a new event:

1. Add the typed struct in
   [`crates/refineid-client/src/events.rs`][events] with
   `EVENT_NAME`.
2. Add the message template to all three `.ftl` files (the
   build refuses to ship if any locale is missing it).
3. Run the test that asserts every event message resolves
   in every locale.

[events]: ../crates/refineid-client/src/events.rs

## Locale resolution at runtime

The renderer needs to know which locale to project a typed
value into. Two distinct use cases:

1. **JSON Lines audit event:** every event carries all
   supported locales (`human.en`, `human.fi`, `human.sv`) so
   the audit log is self-contained and locale-agnostic.
2. **TTY pretty-printer** (future): emphasises one locale for
   terminal display. Picks via `--lang` flag, falling back to
   `LANG` / `LC_MESSAGES` env, falling back to `en`.

## Adding a locale

In principle the bundle layout supports any locale that
Fluent / ICU recognises. In practice the supported set for
refineid is en + fi + sv (the three DVV publishes). Adding a
fourth locale requires:

1. Creating `locale/<lang>/refineid.ftl` with every message ID
   translated.
2. Updating the supported-locales list in the renderer code.
3. Updating the JSON Lines schema -- a new `human.<lang>`
   field appears in every event.
4. SOC ingestion: confirm consumers can handle the new field
   name.

Don't add a locale lightly; the audit-log self-contained
property only holds if every locale is always emitted.

## Open decisions

These were called out during the i18n design discussion and
are not yet locked. Either resolve in a subsequent commit to
this doc, or fill in once a decision is made.

1. **Framework choice.** Mozilla's Fluent (`fluent` /
   `fluent-bundle`) is the strong candidate: built for natural-
   language localization with grammatical agreement (matters for
   Finnish), supports typed args (`DATETIME`, `NUMBER`, plural
   selectors), bundle format (`.ftl`) is human-editable.
   `fluent-static` is a compile-time-checked variant. Plain
   gettext is the alternative; `rust-i18n` is the lightweight
   end of the spectrum.

2. **Wire shape for human prose.** Either all supported
   locales in every event (audit log self-contained, line
   length ~3x) or one locale chosen at emit time
   (`human` + `human_lang`, compact, mixed-locale audit log).
   Default proposal: all locales in every event.

3. **Strict-locale assertions.** Either compile-time (via
   `fluent-static` or a `build.rs` script that parses bundles
   and emits a const list of expected IDs) or runtime (startup
   test that asserts every `EVENT_NAME` resolves in every
   locale). Default proposal: runtime test in the
   `refineid-client` test suite -- failing the build is the
   stronger guarantee but adds toolchain complexity.

4. **Bundle versioning.** Whether a bundle format change
   bumps a schema version visible in the event payload. Not
   urgent until the first incompatible template change.

## Anti-patterns to flag in review

- A locale-specific date string (`"24.10.2022"`, `"10/24/22"`)
  appearing in a Rust `format!` or string literal.
- A natural-language string literal that varies by locale,
  inlined in code rather than in a bundle.
- Code that reads `LANG` and branches on its value to choose
  prose -- the framework handles that, not the business code.
- A new event whose template is added to `en/refineid.ftl`
  but not the others ("translate later"). Either ship all
  locales or don't ship the event yet.
- Audit-log `card_issued` field formatted as anything other
  than ISO 8601. Operator-facing `human.*` fields, fine.
